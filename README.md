# 供应链网络 · Supplier Mesh

以产品为中心的供应链关联网：说一个产品（如"我想做一个智能手表"），系统就把它拆成模块 → 工序 → 工艺能力，
再从供应商库里把能承接每道工序的企业挂上去，织成一张以产品为圆心发散的网。同时保留原有的自然语言寻源、
多维筛选与实地审核清单能力。

## 平台定位与数据壁垒

**供应商的「美团」**：供应商是商家，采购企业是用户，平台用真实履约数据替代不可验证的主观推荐。
完整推演见 [`docs/positioning.md`](docs/positioning.md)，思考过程归档在 Obsidian《供应商寻源台》。

五层里只有后四层算墙，第一层只是门票：

| 层 | 壁垒 | 本仓库的着落点 |
| --- | --- | --- |
| L1 | 数据覆盖（**门票，不是壁垒**） | `ingest/`、`provider/qcc`、`catalog/` |
| L2 | 履约数据（买不到、爬不到） | `srm/` 订单-交付-IQC-8D → `qcdst/` |
| L3 | 网络效应（跨买家聚合） | `service/supplier_ops.go` 样本量加权 + 分歧度 |
| L4 | 转换成本（工具 → 系统） | SRM 沉淀 + `srm/audit.go` 审计留痕 |
| L5 | 合规授权 | 数据来源字段、演示数据标识、待补的授权链 |

**接口层已强制执行的约束**（`internal/policy`）：

- 单页上限 30 条、免认证最多翻到 300 条 —— 挡住用 `page_size=10000` 一个请求拖走全库。
- 单 IP 每分钟 600 次，超出返回 429 + `Retry-After`。阈值定得偏宽是刻意的：限流按 IP 计，而企业出口常是几十人共用一条 NAT，定太紧第一个误伤的是正常客户。**它只是减速带，真正的墙是字段分层。**
- 每个响应带 `X-Trace-Id` 水印。技术手段约束的是"能不能拿"，水印约束的是"敢不敢传"——泄露的文件能反查到具体账号。
- `GET /api/v1/meta/policy` 把规则做成机器可读的契约，`/policy` 页面把它翻译成人话。

**没有实现、也不打算提供的东西**：任何 CSV / Excel / 批量导出端点。
这不是懒，是因为一次导出就能把平台从"决策工具"降级成"数据源"：数据会被转售、被建库、被脱离上下文传播，
评级的样本口径与分歧度提示也随之丢失，反而误导使用者。替代方案（受控对比视图 + API 配额）写在策略接口里 ——
**只拒绝不给出路，用户会直接走人。**

## 数据真实性

**系统默认不加载任何生成的供应商数据。** 启动后是一张空网，直到你接入真实数据源。

- 真实来源：企查查 / 天眼查导出的工商信息表（CSV），或企查查开放平台 API。
- 字段缺失就留空，界面显示"—"，绝不填充看起来合理的值。
- 每条记录带 `data_source`、`last_verified_at`、`source_url`，档案面板里可点回原始记录。
- `GET /api/v1/meta/dataset` 返回 `is_real`；不为 `true` 时界面顶部会挂红色警示条。
- `SUPPLIER_SOURCE=mock` 仅供开发联调，会被全程标记为「非真实数据」。

接入步骤见 [`docs/real-data.md`](docs/real-data.md)。

## 快速启动

```bash
# 后端（先接数据源，否则是一张空网）
cd backend
SUPPLIER_SOURCE=csv SUPPLIER_CSV=data/suppliers.csv go run ./cmd/server

# 或者走企查查开放平台
SUPPLIER_SOURCE=qcc QCC_KEY=xxx QCC_SECRET_KEY=xxx SUPPLIER_NAMES=data/companies.txt go run ./cmd/server

# 前端
cd frontend && npm install && npm run dev
```

前端 `http://localhost:3000`，后端 `http://localhost:8080`。`docker compose up --build` 可一键起完整环境。

| 视图 | 入口 | 说明 |
| --- | --- | --- |
| 产品发散网 | `/` 或 `/?q=智能手表` | 产品 → 模块 → 工序 → 供应商四层放射网，含同工艺替代边、同城协同边、单点风险洞察 |

## 节点与连线

- **产品**：圆心。产品配方来自 `backend/internal/catalog/recipes.go`，未知产品会兜底按通用电子消费品的模块结构拆解。
- **模块**：结构件、显示与触控、能源与充电等，按"体量"分配扇区角，重的模块占更多空间。
- **工序**：具体工艺要求（如 AMOLED 显示模组、异形聚合物电芯），带关键/常规标记。
- **供应商**：图上显示简称，悬停给全称；点开是完整工商档案。
- **连线**：`bom` 产品-模块、`process` 模块-工序、`supply` 工序-供应商、`alternative` 同工艺可替代、`same_city` 同城协同。

## 供应商档案字段

工商登记：统一社会信用代码、法定代表人及职务、经营状态、企业类型、成立日期、注册资本/实缴、参保人数、
员工总数、注册地址、经营地址、经营范围、年营业收入、厂房面积、专利数量、分支机构、纳税信用等级、进出口权。

治理与风险：股权结构（股东、持股比例、认缴出资）、主要人员（董事长/总经理/监事）、资质证书（名称/发证机构/
有效期/覆盖范围）、司法与经营风险标签、品牌客户、MOQ、交期、产能利用率。

## 供应商能力评估：QCDST

图谱回答"去哪找供应商"，QCDST 回答"这家到底靠不靠谱"。两者共用同一份供应商主数据。

| 维度 | 权重（通用） | 权重（工业装备） | 主要指标 |
| --- | --- | --- | --- |
| Q 质量 | 30% | 30% | 来料批次合格率、来料不良率 PPM、首件一次通过率、整改按期闭环率、重大质量事故 |
| C 成本 | 20% | 15% | 价格竞争力（对标同品类中位价）、年度降本、成本拆分意愿、账期水平 |
| D 交付 | 25% | 22% | 准时交付率 OTD、交期承诺达成率、订单满足率、紧急插单弹性 |
| S 服务 | 15% | 13% | 平均响应时长、问题解决周期、协同配合度（三方评审） |
| T 技术 | 10% | 20% | 关键工序覆盖度、研发投入强度、新品导入成功率、设备自动化水平 |

权重按品类自动切换：供应商能力标签里出现 CNC / 压铸 / 冲压 / 焊接 / 电机 / 模具时，判为工业装备，
技术维度提到 20%（工业客户里"技术不达标"是硬门槛，比便宜 5% 重要得多）。

三条硬规则，决定了这套分数能不能信：

1. **每个分数都能追到单据。** 指标展开后能看到分子、分母、样本量、计算公式、对标基准，
   以及最近几条可回查的批次号 / 事件号。人工评审项会标注评审人与评审日期。
2. **没有数据就不给分。** 缺报价时成本维度返回 `-1` 并显示"证据不足"，而不是 0 分 ——
   把"没录"算成"做得差"是这类系统最常见的错。
3. **样本不足不评级。** 交付批次少于 15 个一律标"观察期"，分数保留但不出正式评级、不参与排名。
   5 个批次算出来的 95 分和 300 个批次的 95 分不是一回事。

## 轻量 SRM

企业侧工作台（`/srm`）：建立采购方与供应商的合作关系，录入订单、交付批次、IQC 结果、质量事件、报价、服务工单与现场评审。
供应商侧共用同一套单据结构填报，双方看到的是同一份事实。

所有 QCDST 指标都由这些单据实时算出，没有人工调分入口。这是"评级可被审计"的前提。

## 平台级综合评级

`/ranking` 把多家采购方对同一家供应商的评估按样本量加权合并：

- 权重 =（订单数 + 批次数）× 该次评估的置信度。交付 300 批的客户比只试了 5 批的客户说话更重。
- **分歧度**（各买方总分的标准差）单独列出。均分 90 但分歧 18，说明"有人很满意、有人踩过坑"，
  比均分 85 分歧 2 更值得警惕。
- 有效评级买方数不足 2 家时显示"单一买方"，不假装有跨企业数据。

## 寻源 ⇄ SRM 闭环

公开寻源池与企业私有 SRM 是同一套数据的两个域，靠一条单向可信的回路接起来：

```
[公开域] 供应商主数据 + 平台评级
            │  浏览、比选
            ▼
        企业点「引入 SRM」→ 合作关系（candidate）
            │
[私有域]  转 active → 下发订单、收报价、录交付与 IQC、记质量事件
            │
        每张订单独立出 QCDST 评分卡（对账 / 追责）
            │
        供应商级 QCDST 由全部原始单据聚合（评级 / 选择）
            │
[公开域]  跨采购方按样本量加权 → 更新平台评级 → 下一个新用户看到
```

三个刻意的设计决定：

1. **「看中了」不等于「在合作」。** 从寻源引入默认落在 `candidate`（候选），不产生任何单据，
   也不进评分池。候选关系不计入买方数 —— 否则"3 家企业都在用"会被"我关注了它"伪造出来。
2. **订单级分与供应商级分不互相平均。** 订单级用于对账追责（大单小单等权），
   供应商级由全部批次按指标聚合（用于评级）。界面上同时给出两个数字和它们的口径差异说明。
3. **订单级只按判得出来的维度加权。** 一张还没发货的单判不了质量，没有历史报价判不了成本。
   缺的维度直接退出分母，既不按 0 分也不按满分；可判维度权重合计低于 50% 不出评级。

进入公开池的只有聚合后的分数、样本量与买方数；订单金额、单价、质量事件细节不会出现在公开接口里。

合作关系状态机：`candidate → invited → active → paused / terminated`。
已终止的关系不能直接恢复为 `active`，必须先退回 `candidate` 重新评估 —— 终止通常有质量或合规原因。

## 产品 BOM 知识库

`/bom` 收录 14 个可拆解产品，覆盖消费电子（手机 / 手表 / TWS / 音箱 / 移动电源 / 无人机）、
家电（扫地机器人 / 空调）、智能家居（门锁）、出行（电动自行车）与工业装备（六轴机器人 / 伺服关节 /
加工中心 / 控制柜），共 400+ 部件。

| 层级 | 回答什么问题 |
| --- | --- |
| 产品 → 大类（模块 / 总成） | 这个产品值不值得做，哪几块占成本、哪几块卡脖子 |
| 大类 → 小类（部件品类） | 这一类料谁能供 —— 小类是跨产品复用的字典，18 类，不允许各产品自造词 |
| 小类 → 部件 | 具体要什么工艺，落到工艺能力，再落到供应商 |

部件结构整理自公开拆解资料与公开 BOM 目录（bomwiki 等），标注单机用量与关键件，用于寻源下钻，
**不代表任何具体机型的官方 BOM**。

## 部件 → 供应源

`/bom` 的「供应源」视图把 BOM 和公开寻源池接起来：选一款产品，先给出**供应覆盖体检**
（哪些小类是缺口、哪些是单点、哪些关键件卡脖子），再点开小类看候选供应商。

**适配分 = 工艺覆盖 70% + 区域 30%，不含评级分。** 评级是历史表现，适配是能力覆盖。
混在一起会出现"分数很高但工艺根本不对口"的供应商排在前面 —— 这是选错供应商最常见的原因。
评级单独列，没有评级显示"暂无"而不是 0 分，新供应商不该被系统性埋掉。

覆盖风险按公开池中对口供应商家数分级：

| 等级 | 判定 | 该做什么 |
| --- | --- | --- |
| 缺口 | 0 家 | 自行开发或调整设计选型 |
| 单点 | 1 家 | 关键件单点 = 断供即停线，量产前必须锁第二源 |
| 偏窄 | 2-3 家 | 再储备 1-2 家并做小批量验证 |
| 充足 | ≥4 家 | 按评级与适配分择优 |

矩阵的价值不在"找供应商"，而在**提前暴露卡脖子项** —— 等到量产前才发现某颗料单点供应，
代价是改板或停线。供应商页的「可供应部件范围」是反向视角：这家能覆盖哪些小类，
其中"可自制"（主工艺直接命中）与"需外协"（仅小类工艺相关）分开统计，不夸大能力边界。

## 核心接口

- `GET /healthz`
- `POST /api/v1/graph/build` — 产品发散网（`query` / `max_suppliers_per_process` / `region` / `critical_only`）
- `GET /api/v1/graph/mesh` — 供应链全域网
- `GET /api/v1/graph/supplier/:id` — 单家供应商的自我中心网（替代供应商、同城伙伴）
- `GET /api/v1/meta/dataset` — 当前数据集来源、是否真实、导入条数与被跳过的记录
- `GET /api/v1/meta/policy` — 数据开放策略：四层访问范围、字段边界、接口配额、可导出范围
- `GET /api/v1/catalog/products` — 产品库与各自供应商规模
- `GET /api/v1/catalog/capabilities` — 工艺能力库
- `POST /api/v1/suppliers/search` — 自然语言寻源
- `GET /api/v1/suppliers/:id` — 供应商工商档案
- `POST /api/v1/suppliers/:id/audit-checklist` — 实地审核清单

QCDST / SRM：

- `GET /api/v1/qcdst/ranking` — 平台综合评级榜（跨企业加权、分歧度）
- `GET /api/v1/qcdst/supplier/:id?tenant=` — 单家供应商的五维明细与证据链
- `GET /api/v1/qcdst/briefs?tenant=` — 寻源页索引：每家的平台评级 + 本企业合作状态
- `GET /api/v1/qcdst/loop?tenant=` — 闭环体检：池子规模、可信阶段、本企业贡献
- `GET /api/v1/srm/workspace?tenant=` — 采购方工作台（合作关系、评估列表、汇总指标）
- `GET /api/v1/srm/tenants` / `POST /api/v1/srm/tenants` — 租户列表 / 登记企业
- `POST /api/v1/srm/engagements` — 引入供应商（去重，默认候选，记录来源渠道）
- `POST /api/v1/srm/engagements/status` — 推进合作关系状态
- `GET /api/v1/srm/orders?supplier=&tenant=` — 逐单 QCDST 评分卡 + 与供应商总分的口径对照
- `POST /api/v1/srm/orders` / `deliveries` / `quality-events` — 录入业务单据
- `POST /api/v1/srm/demo/seed` / `demo/clear` — 载入 / 清空演示数据

BOM：

- `GET /api/v1/bom/products` — 产品目录、板块分组、小类聚合
- `GET /api/v1/bom/products/:code` — 单产品的完整 BOM 树
- `GET /api/v1/bom/facets` — 按小类聚合（每类被多少产品用到、多少关键件）
- `GET /api/v1/bom/match?q=` — 用一句话匹配已收录产品
- `GET /api/v1/bom/products/:code/supply?tenant=&region=` — 产品供应覆盖矩阵（大类 → 小类风险）
- `GET /api/v1/bom/supply?category=&product=&tenant=&region=&capability=` — 小类候选供应商 + 覆盖体检
- `GET /api/v1/supplier/:id/parts` — 供应商反查：能覆盖的小类与具体部件（可自制 / 需外协）

## 架构说明

`SupplierRepository` 是数据访问边界，当前实现为内存索引，数据由 `repository.BuildDataset` 从真实来源装配。
`internal/ingest` 负责把外部表标准化并从经营范围推断工艺能力，`internal/provider/qcc` 是企查查适配器；
接天眼查等其他平台只需再加一个返回 `ingest.Record` 的客户端。
`catalog` 包是产品-模块-工序-工艺能力的知识底座，改这里就能扩展新品类的拆解规则。
`service/graph.go` 负责组网与风险洞察（缺供、单一供应源、区域集中度、关键供应商风险）。
`internal/qcdst` 是评分引擎（指标定义、归一化、权重、评级门槛、置信度；`order.go` 是订单级评分卡），
`internal/srm` 是单据存储与演示数据，`service/closed_loop.go` 是寻源与 SRM 之间的接缝
（引入去重、状态机、评级索引、闭环体检）。
`catalog/bom*.go` 是产品 BOM 知识库与 18 类部件小类字典。
`internal/policy` 是数据开放策略：分层、字段边界、配额常量都集中在这里，接口与页面共用同一份定义，
避免"文档说锁了、代码没锁"。改这里的常量就等于改全站约束，所以刻意只有一处。
前端 `lib/layout.ts` 用"放射环 + 扇区加权 + 碰撞分离"做布局，`components/NetworkGraph.tsx` 是 SVG 画布
（滚轮缩放、拖拽平移、拖拽节点微调、悬停高亮邻居）。
